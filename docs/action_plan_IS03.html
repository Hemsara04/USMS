3. Detailed Technical Resolution of Panel Directives

3.1 Practical Student Verification & Institutional Assumption Modeling

Panel Understanding: Undergraduate project teams do not have access to live University of Colombo Student Information System (SIS/ERP) APIs due to institutional security protocols and privacy policies. The panel confirmed it is appropriate to model external verification as an engineering assumption.

Technical Resolution: USMS adopts a resilient Two-Tier Verification Architecture:

  • Operational Tier (Internal Verification Queue): In views/admin_user_management.php and sport_application, student-athletes provide their institutional Index Number, Academic Year, and Faculty during registration. Records enter a pending administrative queue where Admins and TICs verify submitted credentials and approve/reject applications with full audit logging.
  • Architectural Tier (External Verification Adapter): The system defines a service adapter interface (StudentVerificationInterface). When institutional API access is officially provisioned, the adapter can connect directly without refactoring existing database schemas or controller logic.

3.2 Elevating Security to Explicit Functional Requirements (FR)

Security has been refactored from general non-functional claims into six demonstrable Functional Requirements, fully implemented in the active codebase:

FR ID Functional Requirement Technical Implementation Verification Reference
FR-SEC-01 Cryptographic Password & Secret Hashing BCRYPT adaptive hashing with automatic unique salt generation via PHP password_hash(..., PASSWORD_BCRYPT). models/User.php:68, 93, 136
models/Admin.php:198
FR-SEC-02 Role-Based Access Control (RBAC) Strict authorization enforcement across 8 system roles (Admin, Coach, TIC, Medical Officer, President, Athlete, etc.). config/auth_guard.php executes requireRole() on Line 1 of all views.
FR-SEC-03 Session Lifecycle & Invalidation Secure session generation upon login, session hijacking defense, and complete cookie/session destruction on logout. AuthController.php:42-97 and AuthController.php:327-340
FR-SEC-04 SQL Injection (SQLi) Immunity 100% Parameterized Prepared Statements across all queries; elimination of raw query string concatenation. config/db.php enforces PDO::ATTR_EMULATE_PREPARES => false.
FR-SEC-05 Cross-Site Scripting (XSS) Sanitization Strict context-aware character escaping for all database and user inputs before rendering into the DOM. Universal application of htmlspecialchars(..., ENT_QUOTES) in views.
FR-SEC-06 Append-Only Administrative Audit Trail Logging of security-critical administrative activities (role modifications, account deletions, verifications). Maintained in views/admin_audit_logs.php logging user, timestamp, IP, and status.

3.3 Multi-Sport Architecture & Complete Scope Coverage

The panel reinforced that USMS must comprehensively support all recognized university sports. Our database schema and software architecture achieve complete multi-sport scalability through normalized entities:

  • Dynamic Sports Entity (sports): Maintains program categories (Indoor, Outdoor, Racquet, Aquatic), program types (Men's Varsity, Women's Varsity, Co-ed Club), and roster constraints.
  • Relational Decoupling: Operational entities—training_sessions, fixtures, match_squads, equipment, and injuries—are relationally mapped to sport_id via indexed foreign keys rather than static enums.
  • Administrative Sports Catalog: Via views/admin_sports_catalog.php, athletic administrators can register and configure new university sports dynamically without source code modification.

3.4 Clinical Discretion vs. Automated Medical Lock Release

Hazard Identified by Panel: Automating medical clearance based solely on elapsed recovery time introduces severe clinical and institutional liability. An athlete could return to competition with unresolved physical trauma.

Remediation Implemented: Automated lock expiration has been permanently removed. Medical clearance is strictly restricted to certified clinicians through the Medical Officer portal (views/med_clearance.php and models/Medical.php), requiring clinical examination and manual sign-off.
